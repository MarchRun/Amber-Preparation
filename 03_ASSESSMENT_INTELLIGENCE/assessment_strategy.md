## 1. Strategic position

- **Unmeasured depth:** algorithms, SQL, database design, testing, system design and English reading/writing/speaking.
- **No documented project evidence:** Java/.NET/Angular/Flutter. Cognitive pace has no observed baseline.

The strategy is therefore:

1. **Protect the gate:** maximise CCAT score through pacing, not perfection.
2. **Differentiate on structure:** business case answers should be clear, practical, and client-aware.
3. **Neutralise gaps:** be honest and show a learning method; never bluff.
4. **Leverage evidence:** use real projects to answer behavioural and technical questions.
5. **Communicate simply:** short sentences, clear signposting, check understanding.

## 2. Stage-by-stage playbook

### Stage 1 — CCAT

**Objective:** 30+ correct, 40+ attempted.

**Rules:**
- 20-second decision rule.
- No blanks.
- Scratch paper only if permitted by actual instructions.
- On a hard multi-step item, guess and advance; return only if navigation explicitly allows it.
- In final minutes shorten hard-item decisions, but still solve immediate items; do not automatically guess everything.

**Mental reset:** If the first question is hard, make a best guess and advance. The test is mixed; do not assume you can return.

### Stage 2 — Programmer Business Case

**Objective:** Demonstrate requirement analysis, practical design, and clear communication.

**Opening (first 2 minutes):**
> "Thank you. Before I propose a solution, I would like to clarify a few things: the primary business goal, the main users, the scope for a first version, and any constraints on timeline or existing systems."

**Structure:**
1. Clarify
2. Restate
3. Decompose
4. Design
5. Trade-offs
6. Next steps

**If coding is required:**
- Confirm language and scope.
- State the approach.
- Write pseudocode first if allowed.
- Implement a thin vertical slice.
- Test edge cases.
- Explain complexity.

**If the case is ambiguous:**
- State assumptions explicitly.
- Propose the smallest useful version.
- List what you would validate with stakeholders.

### Stage 3 — Possible interview

**Objective:** Build trust, show coachability, confirm fit.

**Answer formula (behavioural):** STAR + learning.
- Situation
- Task
- Action (your ownership)
- Result
- Learning

**Answer formula (technical):** Definition → example → trade-off → limitation.

**Answer formula (unknown tech):** Honest gap → closest transferable experience → learning plan.

## 4. Handling the technology gap

### Java
> "I have no documented Java project. C++ and TypeScript give me typed-programming concepts, and my Python game documents OOP exposure. I would need Java and framework practice; I would start with a small tested service following the team's conventions."

### .NET
> "I have no documented .NET project. HTTP, SQL and typed-programming concepts transfer, but I would need C# and framework practice. I would agree a small reviewed task and learning checkpoint rather than promise a fixed time to productivity."

### Angular
> "I have built React and Next.js applications with TypeScript. Angular uses components, services, and dependency injection, which are different patterns, but the separation of UI and data logic is familiar. I would focus on RxJS and Angular's module structure first."

### Flutter
> "I have not shipped a Flutter app. I understand it uses Dart and a widget tree, similar to component composition. I would start with a small offline-capable CRUD app to learn state management and platform integration."

### Oracle/Odoo
> "I have not configured an ERP. I understand the data-integrity and process-mapping challenges from building role-based internal systems. I would learn the specific module and its constraints before proposing customisations."

**Never say:** "I can learn anything in a week." Instead: "I can become productive in the basics quickly, and I would need mentoring on the platform-specific parts."

## 5. English communication rules

1. **Short sentences.** One idea per sentence.
2. **Signpost.** "There are three parts to my answer."
3. **Pause.** Silence is better than filler.
4. **Ask.** "Does that answer your question?"
5. **Repair.** "Let me rephrase that."
6. **Admit.** "I don't know that term. Could you clarify?"
7. **Slow down.** Nerves speed you up; deliberately slow your rate.

Avoid:
- Long memorised paragraphs.
- Fancy vocabulary you cannot pronounce.
- Filler ("basically," "you know," "kind of").
- Apologising for your English.

## 6. Decision rules

| Situation | Rule |
|---|---|
| Instructions unclear | Ask one precise question |
| Task too large | State assumptions; deliver a thin slice |
| Unknown technology | Honest gap + transferable skill + learning plan |
| Challenged on design | Restate constraint; adjust or defend with evidence |
| Running out of time | Summarise what is done and what remains |
| Asked about salary | Defer to later stage unless pressed; give a researched range if needed |
| Asked about weaknesses | Real weakness + active mitigation |
| Asked "any questions?" | Ask one thoughtful question about the role/team |

---

## 7. Red flags to avoid

- Overclaiming experience.
- Arguing with the evaluator.
- Ignoring non-functional requirements.
- Designing for millions of users when the prompt says 50.
- Speaking over others in a group.
- Blaming teammates or tools.
- Giving a 5-minute answer to a 1-minute question.
- Checking your phone.
- Badmouthing previous employers or university.
